# Independent music module

The module stores personal music data in Postgres through GORM and plain, uncached SQL. It does not use the shared management Bearer, the Bot instance tenant ID, browser NetEase login, QR codes, client-supplied music cookies, refresh goroutines, unlock services, or cross-source matching. An optional pre-existing operator-owned source authorization stays in the server environment and never becomes a music-user identity. `source:externalID` identifies a recording. Guest identities are random; verified identities use `(application ID, actual Feishu tenant_key, verified open_id)`.

The same `internal/music.Module` runs inside `cmd/larkrobot` or in `cmd/music-server`. It is disabled in the Bot unless `MUSIC_ADDR` is set. Prefer the separate executable for an independent deployment; no Bot restart is necessary. No administration, health, model, or Bot messaging endpoints are exposed on its listener.

## Configuration and migration

Use `deploy/music.env.example` as a list of variable names. Supply actual values via a private environment/secret manager. Never commit an actual environment file. An enabled module requires an exact `MUSIC_ORIGIN` and an explicit `MUSIC_APP_ID`. Use different app boundaries for master/next applications. Configure HTTPS and `MUSIC_COOKIE_SECURE=true` in production. Keep the database and catalogue adapter on private networks.

`script/sql/20261113_music.sql` is additive and registered in the standard schema migration list. The standalone module applies the same SQL in a transaction. An advisory transaction lock serializes music schema setup. No existing Bot tables are altered. The additive `20261113_music_canonical.sql` migration marks prior catalogue rows unverified until the configured provider repairs them. The original music migration checksum remains unchanged. Client descriptor/import metadata no longer defines shared catalogue rows: imports use provider metadata or verified cache. Uncached imports require an available provider; unsupported new source IDs are rejected. Existing unsupported owned records remain exportable, but generic track APIs cannot claim them. Back up the database before production migration. The migration role needs CREATE TABLE/INDEX; the runtime role needs SELECT/INSERT/UPDATE/DELETE on music tables. When runtime DDL is disallowed, run the additive migration separately and set `MUSIC_MIGRATE=false`; startup then verifies that all nine tables and the canonical verification column exist without issuing DDL. Do not grant access to unrelated Bot tables just for music.

Build with the Go version from go.mod and repository baseline:

```sh
BETAGO_CONFIG_PATH=/absolute/main-workspace/.dev/config.toml \
  go test -tags=custom_skip_vips -v ./internal/music ./cmd/music-server
BETAGO_CONFIG_PATH=/absolute/main-workspace/.dev/config.toml \
  go build -tags=custom_skip_vips -trimpath -o music-server ./cmd/music-server
```

The focused persistence tests additionally require `TEST_MUSIC_DSN` targeting an **isolated database whose name contains music_test**. They truncate only music tables there. Add `-race` for concurrency validation. The binary does not load Bot credentials or initialize Bot infrastructure.

A private Postgres 15+ database is sufficient. The music tables are `music_users`, `music_sessions`, `music_tracks`, `music_playlists`, `music_entries`, `music_likes`, `music_history`, `music_queues`, and `music_shares`. Session and recovery secrets and share tokens are random 256-bit values, SHA256 hashed at rest. Expired sessions/shares cannot authenticate; scheduled deletion of expired rows can be added to existing operational maintenance. Playlist deletion retains a tombstone. Do not remove tombstones while stale clients may remain.

## Web deployment

Build the associated `betago-music-web/frontend` application with Node >=22.12 and `npm ci && npm run build`. The current application uses Vue 3, TypeScript, Vite and Pinia; the older YesPlayMusic implementation remains reference material only. The static frontend talks only to same-origin `/music-api/v1` for personal data and anonymous catalogue access. Use its Nginx configuration or set `MUSIC_STATIC_DIR` on the standalone server. The Nginx configuration avoids logging URL query strings or share tokens. Never proxy this prefix to the administration API.

The local deployment serves the static build and this API independently of the Bot. It requires `MUSIC_DATABASE_URL` and `MUSIC_ORIGIN`; it does not provision or restart an existing Bot. Personal APIs use `Cache-Control: no-store`. Revalidate any older container packaging against the current frontend build before using it for production.

For anonymous catalogue access, set `MUSIC_NETEASE_URL` to an independently verified anonymous Netease API. The default is anonymous. If the operator deliberately configures `MUSIC_NETEASE_COOKIE`, it is sent as a Cookie header only to this exact trusted API; redirects are disabled, and no login/QR/refresh or user-account binding is added. Keep the authorization in private secret configuration, never URLs, client bundles or reports. The Go adapter requests `unblock=false`; it honors unavailable/preview results and rejects media hosts outside official NetEase music domains. MUSIC_OWNED_MEDIA_HOST is a legacy exact-host opt-in and must not authorize an automatic matching service; it does not permit nonofficial media to enter the new cache writer. The compatibility /song/url endpoint is tried once only after a transport/decoder error from /song/url/v1, and its media host is checked identically. No source URL is persisted as a stored audio source. Official HTTP audio is upgraded only after an independent cookie-free HTTPS HEAD verification, with a one-byte Range GET if HEAD is unsupported; otherwise the result is unavailable. Track JSON serializes artwork safely even from old verified database rows: only p1/p2/p3/p4.music.126.net HTTP is upgraded and unknown HTTP artwork is blank. Resolve returns an expiring URL (provider lifetime capped conservatively at 5 minutes), status and reason. Browser errors trigger at most one re-resolution per selected track and restore progress after loading; persistent failure stops visibly. H5 background/lock-screen behavior remains controlled by the browser and operating system.


## Explicit MinIO source and bounded caching

Set `MUSIC_MINIO_CACHE_ENABLED=true`, internal `MUSIC_MINIO_ENDPOINT`, exact HTTPS `MUSIC_MINIO_PUBLIC_ORIGIN`, and secret `MUSIC_MINIO_ACCESS_KEY` / `MUSIC_MINIO_SECRET_KEY`. Optional bucket defaults to cloudmusic and region to us-east-1. The public GET/HEAD object proxy must preserve the external Host including its port for S3 signatures. Do not allow object mutation or bucket listing through it, and do not log signed query strings. The standalone command and runtime.Module use the same provider construction; invalid enabled configuration fails startup rather than silently disabling protection.

The read-only default checks fixed catalogue/info, audio, lyrics and picture objects for a stable numeric NetEase ID. Metadata and audio object are validated before signing a 300-second HTTPS audio URL. Old audio/lyrics URLs and arbitrary descriptor paths are ignored. Fixed `picture/<id>.jpg` is exposed through a stable, public, read-only API artwork endpoint that returns a no-store307 to a fresh signature; no private non-music bucket is reachable. Only absent objects fall through to the same recording in the configured catalogue. Cache permission errors, corrupt metadata and transport outages do not trigger a hidden source fallback.

Optional `MUSIC_MINIO_CACHE_WRITE_ENABLED=true` requires write capability to fixed music/, lyrics/ and catalog/ prefixes, in addition to read access. A complete official HTTPS source resolution can be cached synchronously with same-process per-ID singleflight and two writer slots. Each fill is bounded to 12 seconds within the existing request deadline and 64 MiB; it sends no service-account cookie to the CDN and forbids redirects. An existing audio object lacking trustworthy metadata is preserved without downloading or writing; the source response is labelled cache_skipped_existing_unverified_audio. Stat errors skip caching. New PUTs all use If-None-Match:* to prevent races from overwriting existing objects. Content-Type and ID3/MPEG header checks reject HTTP200 error pages or other source formats before any upload. Audio PUT completes first, trusted lyrics are attempted, and a versioned catalog/<id>.json is written last as the commit marker. Existing info/<id>.json is not overwritten. A failed manifest is never a cache hit; incomplete/orphan uploads can be reviewed later without deleting personal library data. Preview and restricted recordings never become full cache entries. Results disclose stored, failed, busy or preview-skipped caching in reason. Same-ID coalescing is process-local; multi-replica distributed locking is outside this MVP.

Disable WRITE_ENABLED to return to read-only use; disable CACHE_ENABLED to remove this explicit source on the next isolated service restart. Leave existing objects and personal tables intact. Replacing optional source authorization does not require changing music users, sessions or Feishu identity. Runtime activation, real signed Range reads, expiry/re-sign and real-account playback must be verified separately; deterministic provider/S3 tests alone are not real-song acceptance.

## Optional Feishu identity

The backend exchanges a temporary code at the official v2 token endpoint, then calls user_info with that server-held token. Missing tenant_key/open_id or a rejected exchange fails closed. Tokens are never returned to the browser or persisted. Configure the actual app ID, app secret, redirect URI, required app permissions, and the app's allowed web domain. The browser reads the public `/music-api/v1/auth/options` endpoint instead of embedding a second application ID at build time. It contains only guest availability and configured Feishu enabled/appID fields; it issues no session and exposes no secrets. Configuration discovery does not prove that the app permissions and domain are approved. The host must provide the official Feishu `tt.requestAccess` JSSDK capability. External browsers retain guest access. Missing server configuration returns 503 `feishu_not_configured`; a rejected temporary code returns 401 `feishu_code_rejected`. This flow has protocol tests; it requires a real approved Feishu web app and client for production verification. No claim of successful real Feishu authorization is made.

Guest and Feishu spaces are separate identities. Export guest playlists/likes and import after switching if copying is desired. The guest recovery flow restores the same guest space using a separately rotated secret; a read-only share link cannot recover or own that account. Clearing browser data without a recovery code or JSON backup loses the entry to a guest space. This is not automatic cross-device identity.

Official references: [token exchange](https://open.feishu.cn/document/authentication-management/access-token/get-user-access-token), [verified user info](https://open.feishu.cn/document/server-docs/authentication-management/login-state-management/get), [H5 login](https://open.feishu.cn/document/client-docs/h5/development-guide/step-3).

## Rollback

1. Keep the previous frontend image/build and API binary available. Restore the prior static build and stop only this independent music service, or unset MUSIC_ADDR for its next Bot deployment.
2. Leave the additive music tables intact. Rolling back code must not drop personal data, reset revisions, or revive tombstones. Do not reintroduce personal cookie initialization just to provide guest playback.
3. Restore a database snapshot only as an explicitly planned recovery; it can roll back revocations and revisions. Revoke/reissue sessions and shares after such recovery.
4. Reverting to the pre-MVP card implementation also reintroduces its old login initialization. Treat that as a separate compatibility decision, not an automatic part of music-service rollback.
